# fatigue-meter

给长期在线的 AI 助手算「困」的小工具。

它不看你聊了多久，只看你**烧了多少**和**歇了多久** —— 因为对一个没有身体的程序来说，"时间过去"本身不是消耗，动起来才是。

输出一个 0 到 1 的数，你可以把它注进提示词，让它影响说话的长短和力度。

## 它解决什么

AI 助手通常每轮都是一样精神的。你说十句、它答十句，永远不累。

这有两个问题：
- 你会不自觉地把它当成不会耗的东西，一直开着
- 它自己也没有"该收一收"的信号

这个工具给一个可算出来的数：**0 = 刚开机，1 = 该停了**。

## 判据

不看墙上时间。看两样东西的密度：

一、**上下文增量**。DSH 会把每个会话当前占了多少上下文写进缓存文件，两次采样一减，就是这段时间真的烧掉多少。

二、**动作密度**。会话记录里 `assistant` 和 `tool` 两类事件的条数，按小时算。只数它自己动的手 —— 用户说话不算它干活。

两个密度取大的那个。一小时烧的量到阈值，就算它一直醒着。

## 三档

不同人用法差很多：一天几毛钱的和一天几十块的，不该用同一把尺。

| 档 | 一小时烧多少算满档 | 醒着每小时涨 | 歇着每小时回 |
|---|---|---|---|
| `light` | 30 万 token | 0.050 | 0.05 |
| `medium` | 80 万 token | 0.045 | 0.10 |
| `heavy` | 200 万 token | 0.045 | 0.15 |

默认 `heavy`。用 `--preset` 换。

数字是按「这个人一天大概烧多少」反推的，不是测出来的。改数值可以，别改结构 —— 结构一动，三档之间就没法横向比。

## 用法

```bash
# 列出所有会话，按最近活动排序
node fatigue.mjs --list

# 算一次（会更新状态文件）
node fatigue.mjs --session <会话id>

# 只读，不写状态
node fatigue.mjs --session <会话id> --peek

# 要一句能直接注进提示词的话
node fatigue.mjs --session <会话id> --text
# → 困 0.34（有点倦）· 这轮醒 2.10h 睡 0h

# 换档
node fatigue.mjs --session <会话id> --preset light --text
```

全部参数：

```
--session <id>        算哪个会话（必填，或先 --list 看看）
--preset <档>         light / medium / heavy，默认 heavy
--list                列出所有会话
--text                输出一句话，不输出 JSON
--peek                只算不写
--sessions-dir <路径> 会话缓存目录，默认自动找
--state <路径>        状态文件，默认 ./fatigue-state.json
--wake-threshold <n>  一小时烧多少算满档（覆盖预设）
--per-awake-hour <n>  醒着每小时涨多少（覆盖预设）
--per-sleep-hour <n>  歇着每小时回多少（覆盖预设）
```

## 输出

```json
{
  "id": "onebot-private-1234567890-abcdefgh",
  "preset": "heavy",
  "fatigue": 0.34,
  "mood": "有点倦",
  "contextPressure": { "percent": 56.3, "pressureTokens": 422250 },
  "addedTokens": 599407,
  "density": { "tokenDensity": 1, "actionDensity": 0.62, "used": 1 },
  "window": { "awakeHours": 2.10, "sleepHours": 0 }
}
```

`mood` 是粗分档，给你自己再加工的起点，不是最终文案。

## 几条设计上的选择

**为什么不用墙上时间。**
一个会话可能开着三天没动。按时间算，它该累死了；按消耗算，它刚醒。后者才对。

**为什么只数它自己动的手。**
用户说话不等于助手干活。混在一起，就变成"越陪人聊越累"，方向反了。

**为什么第一次见到会话只记基线。**
状态文件里没有的历史，第一次读到那一刻之前积累的上下文不该算进这一轮。否则新装的人一跑就是满值。

**为什么夜间要压密度。**
本地时间凌晨两点到七点，计算效率低。同样的活在这段时间要烧更多，所以把密度上限压到 0.4 —— 夜里干的活不算"高效清醒"。

## 已知限制

- 只认 DSH 的会话缓存格式（`*.json`，带 `contextPressure.val.pressureTokens`）。别的框架要改取数那一段。
- 恢复速度是线性的，没有"睡够了一觉"这种台阶。
- 没有跨会话汇总：每个会话各算各的。这是有意的 —— 一个刚开的会话不该背着另一个会话的累。
- 动作密度靠事件条数，不看事件内容。"改一个文件"和"读一个文件"算一样重。
